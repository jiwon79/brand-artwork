# 레퍼런스 복원 이후 새로운 차이를 만드는 작업 방식

이 문서는 시각 레퍼런스를 먼저 복원한 뒤, 원작의 정체성을 유지하면서 새로운 상호작용이나 움직임을 추가할 때 사용하는 공통 작업 방식이다.

특정 작품의 실험 결과, 함수명, 현재 파라미터와 커밋 이력은 넣지 않는다. 그런 내용은 `docs/artworks/<name>/`의 작품별 결정 기록에 둔다.

## 1. 이 가이드를 사용하는 시점

다음 조건을 만족한 뒤 사용한다.

- 레퍼런스의 핵심 화면을 재현했다.
- 정지 화면뿐 아니라 등장, 이동, 사라짐의 시간 특성도 확인했다.
- 같은 입력을 반복해 비교할 수 있는 고정 조건이 있다.
- 현재 차이가 구현 오류인지 의도적인 변형인지 구분할 수 있다.

복원이 아직 끝나지 않았다면 확장 아이디어를 섞지 않는다. 기준이 움직이는 동안에는 새 기능이 좋아진 것인지 원작에서 멀어진 것인지 판단하기 어렵다.

## 2. 레퍼런스 계약을 먼저 쓴다

**레퍼런스 계약**은 바꾸면 그 작품처럼 보이지 않게 되는 특징의 목록이다.

다음 질문에 답한다.

- 가장 먼저 눈에 들어오는 형태는 무엇인가?
- 입력과 최종 화면 사이에서 반드시 유지돼야 하는 계산은 무엇인가?
- 색을 꺼도 남아야 하는 실루엣 특징은 무엇인가?
- 지연, 잔상, 소멸처럼 정지 화면에서 보이지 않는 특징은 무엇인가?
- 사용자의 행동과 화면 반응 사이에서 꼭 유지해야 하는 인과관계는 무엇인가?

계약은 “예뻐 보인다”처럼 넓게 쓰지 않는다.

```text
나쁜 예
  부드럽고 유기적으로 보여야 한다.

좋은 예
  입력 위치가 이동해도 같은 외곽 계산을 사용한다.
  효과의 경계는 원본 도형의 배치에 의존한다.
  입력이 끝난 뒤 결과는 제자리에서 갑자기 사라지지 않는다.
```

## 3. 확장 문장을 한 줄로 제한한다

여러 단계를 동시에 바꾸기 전에 다음 문장을 완성한다.

```text
[레퍼런스의 핵심 계산]은 유지하고,
[하나의 입력 또는 상태]에 [새로운 규칙]을 추가해
[사용자가 느낄 차이]를 만든다.
```

한 문장에 색, 외곽, 입력, 시간 상태와 배경 반응이 모두 들어가면 범위가 너무 넓다. 먼저 주 확장 하나를 고르고, 다른 변화는 주 확장을 설명하는 보조 반응으로 둔다.

## 4. 이미 존재하는 입력 신호에서 후보를 만든다

새 제스처를 먼저 발명하기보다 현재 입력에서 이미 측정할 수 있는 값을 적는다.

- 위치
- 이동 방향
- 속도와 가속도
- 누르고 있는 시간
- 한 위치의 체류 시간
- 이동 거리
- 입력 시작과 종료
- 여러 입력 사이의 거리

그다음 작품의 재료나 주제와 연결할 수 있는 행동 규칙을 적는다.

- 관성
- 점성
- 중력
- 탄성
- 축적과 냉각
- 마찰
- 응집과 분리
- 성장과 침식

후보 하나는 가능하면 **입력 신호 하나 × 행동 규칙 하나**로 만든다. 이렇게 하면 사용자가 무엇을 해서 변화가 생겼는지 분명하고, 문제가 생겼을 때 원인을 추적하기 쉽다.

## 5. 후보 카드를 작성한다

각 후보는 구현 전에 같은 형식으로 기록한다.

```text
후보 이름:
사용하는 입력 신호:
새로 추가할 행동 규칙:
새로 저장해야 할 상태:
계속 유지할 레퍼런스 계약:
재사용할 기존 렌더 단계:
입력 시작 때 보이는 변화:
입력을 유지할 때 보이는 변화:
입력을 움직일 때 보이는 변화:
입력이 끝난 뒤의 변화:
상태가 완전히 끝나는 조건:
가장 큰 구현 위험:
설명 없이도 원인과 결과가 읽히는가:
```

후보를 조합하기 전에 각각 독립적으로 구현한다. 두 후보를 함께 켜면 어느 규칙이 좋은 인상을 만들었는지 알 수 없고, 탈락한 기능의 상태와 파라미터가 제품 코드에 남기 쉽다.

## 6. 후보를 선택하는 기준

다음 항목을 같은 입력 시나리오에서 비교한다.

| 기준 | 확인할 질문 |
| --- | --- |
| 정체성 유지 | 레퍼런스의 핵심 형태와 계산이 그대로 남는가? |
| 인과관계 | 사용자의 행동이 왜 그 결과를 만드는지 설명 없이 읽히는가? |
| 시간 연속성 | 시작·유지·이동·종료 사이에 갑작스러운 전환이 없는가? |
| 상태 독립성 | 과거에 만들어진 결과가 현재 입력에 끌려다니지 않는가? |
| 기존 구조 활용 | 이미 검증한 렌더 단계를 다시 사용할 수 있는가? |
| 차이의 크기 | 단순 파라미터 변경을 넘어 새로운 경험을 만드는가? |
| 디버깅 가능성 | 중간 상태를 분리해 문제 원인을 볼 수 있는가? |
| 매체 적합성 | 실제 기기와 화면 녹화에서도 행동이 잘 읽히는가? |

가장 화려한 후보보다 **레퍼런스의 문법으로 새로운 행동을 설명할 수 있는 후보**를 우선한다.

## 7. 가능한 한 앞단의 원인을 바꾼다

확장할 위치는 다음 우선순위로 찾는다.

1. 입력을 만드는 위치, 방향 또는 힘
2. frame 사이에 유지되는 상태
3. 기존 표면 계산에 들어가는 중간값
4. 완성된 표면이 다른 물체에 주는 반응
5. 최종 합성된 픽셀의 직접 변형

완성된 픽셀을 직접 늘이거나 끌어내리는 방법은 빠르게 보이지만 새 위치의 장면과 관계를 다시 계산하기 어렵다. 가능하면 위치·속도·시간 같은 원인 상태를 움직이고, 기존 renderer가 매 frame 결과를 다시 만들게 한다.

## 8. 시간 상태의 소유권을 정한다

입력이 끝난 뒤에도 남는 효과에는 상태 소유권이 필요하다.

| 질문 | 기록할 내용 |
| --- | --- |
| 생성 | 어느 입력에서 상태가 만들어지는가? |
| 추종 | 어떤 상태가 현재 입력을 계속 따라가는가? |
| 분리 | 입력에서 독립되는 순간은 언제인가? |
| 갱신 | 분리된 뒤 어떤 힘이나 규칙만 읽는가? |
| 종료 | 값 감소, 충돌, 화면 이탈 중 무엇으로 끝나는가? |
| 제한 | 상태 수가 가득 차면 무엇을 합치거나 버리는가? |

분리된 상태가 계속 현재 입력을 읽으면 과거 결과가 새 포인터 위치로 끌려온다. 종료 조건을 정하지 않으면 화면 중앙에서 fade하거나 작은 잔여물이 남는 임시 처리가 들어가기 쉽다.

## 9. 입력의 시간 구간을 따로 검증한다

포인터 기반 상호작용이라면 최소한 다음 네 구간을 따로 본다.

### 9.1 시작

- 첫 frame에 완성된 결과가 갑자기 나타나지 않는가?
- 시작 지연이 의도한 원인과 연결되는가?

### 9.2 유지

- 입력을 유지하는 동안 공급이나 변화가 끊기지 않는가?
- 고정된 입력에서도 경계가 주기적으로 떨리거나 커지지 않는가?

### 9.3 이동

- 현재 입력을 따라갈 상태와 남아야 할 상태가 구분되는가?
- 속도에 따라 조각 수나 크기가 갑자기 달라지지 않는가?
- 이미 만들어진 결과가 현재 입력의 경로를 반복하지 않는가?

### 9.4 종료

- 종료가 새 상태 생성을 멈추는 것인지, 기존 상태를 지우는 것인지 분명한가?
- 기존 상태가 시작 때와 같은 규칙으로 끝까지 움직이는가?
- 종료 직전에 중앙 핵이나 끊어진 꼬리가 남지 않는가?

마우스, 터치, 화면 밖 이동, 빠른 드래그와 긴 Hold를 각각 확인한다.

## 10. 구조 문제와 파라미터 문제를 구분한다

다음 현상은 수치를 조절하기 전에 상태 구조를 확인한다.

| 관찰된 현상 | 먼저 확인할 구조 |
| --- | --- |
| 과거 흔적이 현재 입력을 따라옴 | 분리된 상태가 최신 입력을 계속 읽는가? |
| 이동 경로에 작은 조각이 생김 | 거리마다 작은 상태를 다시 표본화하는가? |
| 중앙만 남고 주변이 먼저 사라짐 | 서로 다른 나이에 같은 수명 fade를 적용하는가? |
| 첫 입력이 갑자기 나타남 | 처음부터 완성 크기나 강도를 넣는가? |
| 하나의 물체가 늘어나거나 찢어짐 | 픽셀마다 서로 다른 변형 상태를 적용하는가? |
| 닿지 않은 대상이 반응함 | 보이지 않는 field나 넓은 경계 상자를 접촉으로 쓰는가? |
| 고정 입력에서 경계가 떨림 | source와 이미 분리된 상태가 같은 자리를 교대로 차지하는가? |

damping, blur, threshold를 바꿔 현상을 숨기기 전에 누가 상태를 만들고, 소유하고, 끝내는지 다시 본다.

## 11. 결과를 층별로 검증한다

가능하면 다음 순서로 중간 결과를 분리한다.

1. 입력과 시간 상태
2. 입력이 영향을 주는 범위
3. 실제 대상과 접촉한 위치
4. 색을 제외한 최종 외곽
5. 보조 물체의 반응
6. 색과 합성을 포함한 최종 결과

처음부터 최종 색 화면만 보면 움직임, 접촉, 외곽과 palette 문제가 서로 가려진다. 실루엣이 핵심인 작품은 먼저 배경·원본 도형·새 효과만 구분한 단색 화면에서 비교한다.

검증 캡처, 측정값과 분석 스크립트는 임시 QA 폴더에 만들고 제품 문서에는 선택 근거만 남긴다.

## 12. 선택한 뒤 정리한다

후보를 선택한 뒤에는 다음 작업까지 마쳐야 결정이 완료된다.

- 선택하지 않은 모드와 분기 제거
- 사용하지 않는 파라미터와 GUI 항목 제거
- 선택된 상태 모델의 이름 정리
- 시작·이동·종료 불변 조건을 테스트 항목으로 기록
- 현재 구조는 artwork 아키텍처에 반영
- 후보와 선택 이유는 artwork 결정 기록에 반영
- 다른 작품에서도 반복할 절차만 이 guide에 반영

실험 코드를 계속 남겨 두면 이후 수정이 어떤 모드에 적용되는지 불분명해지고, 현재 기본값에서 꺼진 기능이 실제 구조처럼 보이게 된다.

## 13. 작품별 결정 기록 템플릿

작품 문서에는 일반론보다 실제 판단 근거를 남긴다.

```text
# [작품명] 확장 아이디에이션과 선택 기록

## 레퍼런스 계약
실제로 유지하기로 한 형태와 시간 특성

## 후보
각 후보가 사용한 입력, 결과, 관찰된 한계

## 선택
무엇을 선택했고 어떤 기준을 통과했는가

## 구조가 바뀐 과정
관찰된 문제 → 원인 상태 → 변경한 모델

## 최종 불변 조건
시작·유지·이동·종료에서 깨지면 안 되는 규칙

## 검증 순서
중간 단계와 실제 기기에서 확인할 장면

## 구현 이력
결정 변화를 확인할 커밋이나 변경 지점
```

## 14. 완료 체크리스트

- [ ] 레퍼런스 계약과 확장 문장이 분리돼 있다.
- [ ] 후보를 독립적으로 비교했다.
- [ ] 새 상태의 생성·추종·분리·종료 조건이 적혀 있다.
- [ ] 기존 렌더 결과가 아니라 가능한 앞단의 원인을 바꿨다.
- [ ] 시작·유지·이동·종료를 각각 검증했다.
- [ ] 구조 문제를 파라미터로 숨기지 않았다.
- [ ] 선택하지 않은 구현을 제거했다.
- [ ] 작품별 기록과 공통 가이드의 내용을 섞지 않았다.
