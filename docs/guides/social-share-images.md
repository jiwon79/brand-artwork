# 소셜 공유 이미지 제작

작품 링크를 공유할 때 표시할 Open Graph·트위터 카드 이미지를 만드는 공통 절차다. 게시물 캡션 작성과는 별개이며, 캡션은 계속 Notion에서 관리한다.

## 제작 원칙

- GPT Image 같은 생성형 이미지 도구를 사용하지 않는다. 기존 작품의 SVG·Canvas·WebGL과 실제 폰트·질감이 합성된 화면을 그대로 렌더링해 캡처한다.
- 기본 산출물은 **1200 × 630 픽셀 PNG**다. 처음부터 PNG로 출력하며, JPEG를 PNG로 변환하거나 파일 확장자만 바꾸지 않는다.
- 완성 파일은 `pages/<artwork>/assets/og-image.png`에 둔다. 이는 배포용 작품 자산이다. 문서에 별도 설명 이미지를 삽입할 때는 `docs/assets/` 규칙을 따른다.
- 브라우저 탭·주소창·개발자 도구·디버그 패널·작업용 포인터가 이미지에 들어가지 않게 한다.
- 기본 목표 용량은 2 MB 이내다. 거친 질감 때문에 커지면 무손실 최적화를 우선하고, 용량을 줄이려고 JPEG로 바꾸거나 질감을 뭉개지 않는다. 이 저장소의 파일 크기 검사 상한은 5 MB로 둔다.

## 1. 실제 작품에서 장면 고르기

1. 현재 작업 트리의 개발 서버를 확인한다. 이미 실행 중이면 재사용하고, 없으면 `pnpm dev`로 시작한다. 이미지 제작 때문에 기존 배포나 Tailscale 설정을 바꾸지 않는다.
2. **기존 Chrome 창**에서 해당 작품을 연다. 캡처용 새 브라우저 프로세스를 띄우지 않는다.
3. 작품을 설명하는 장면을 고른다. 정지 상태가 충분하면 그대로 쓰고, 상호작용이 핵심이면 대표적인 동작이 드러난 순간을 쓴다.
4. 글자가 끝까지 보이고 주요 형태가 잘리지 않는지 확인한다. 별도의 생성형 포스터나 실제 작품에 없는 그래픽을 덧붙이지 않는다.
5. 폰트와 텍스처가 모두 로드된 뒤 캡처한다. 대체 폰트로 찍힌 결과를 최종본으로 사용하지 않는다.

## 2. Chrome에서 PNG 직접 캡처하기

macOS Chrome 기준이다. 자동화 도구의 화면 미리보기는 JPEG일 수 있으므로, 미리보기 바이트를 `.png`라는 이름으로 저장하는 것으로 끝내지 않는다.

1. 개발자 도구를 열고 **Toggle device toolbar**를 켠다.
2. 장치를 **Responsive**, Width를 `1200`, Height를 `630`으로 설정한다.
3. 기기 툴바의 **More options → Add device pixel ratio**로 DPR 항목을 표시하고 `1`로 설정한다. 화면에 맞추는 Zoom과 출력 픽셀 밀도인 DPR은 다른 설정이다.
4. 크기 설정으로 작품이 초기화될 수 있으므로, 설정을 끝낸 뒤 원하는 장면을 다시 만든다.
5. 같은 **More options → Capture screenshot**으로 PNG를 저장한다. **Capture full size screenshot**은 페이지 전체 높이를 담을 수 있으므로 이 고정 비율 카드에는 사용하지 않는다.
6. 저장된 파일을 열어 내용·실제 픽셀 크기·인코딩을 확인한 뒤 작품의 `assets/`로 옮긴다.

PNG 출력을 명시할 수 있는 브라우저 캡처 API를 이미 연결해 둔 경우에도 사용할 수 있다. 단, 기존 Chrome을 재사용하고 결과 파일 검사를 동일하게 수행한다.

### 움직이는 장면을 고정해야 할 때

- 실제 작품의 상태와 렌더러를 재사용해 캡처 순간만 고정한다. 모양을 별도로 흉내 낸 이미지로 대체하지 않는다.
- 필요한 임시 상태 설정은 개발 환경에만 적용한다. 크기 변경·폰트 로드·캡처 도구의 리사이즈가 장면을 초기화하는지도 확인한다.
- 실제 작품 요소가 아닌 자동화 포인터 표시가 남으면 캡처 동안만 제외한다.
- 저장 후 임시 코드·스타일·쿼리 파라미터를 제거하고 일반 입력과 복귀 동작을 확인한다. 캡처를 위해 동작을 멈추는 코드를 제품에 남기지 않는다.
- 브라우저의 기기 모드·DPR·화면 크기 등 임시 설정도 원상 복구한다.

## 3. 파일 형식과 크기 검증

아래 `<artwork>`는 실제 작품 폴더명으로 바꾼다.

```sh
file pages/<artwork>/assets/og-image.png
sips -g pixelWidth -g pixelHeight pages/<artwork>/assets/og-image.png
```

`PNG image data`, `1200`, `630`이 나와야 한다. 파일명만 보고 형식을 판단하지 않는다. Vitest에서는 PNG signature, IHDR의 너비·높이, IEND와 파일 크기를 검사한다.

PNG 원본을 직접 열어 다음을 별도로 확인한다. 자동 테스트만으로 시각적 검증을 대체하지 않는다.

- 실제 작품과 동일한 폰트·색상·질감인가?
- 글자와 핵심 형태가 잘리지 않았는가?
- 커서·자동화 표시·디버그 UI가 빠졌는가?
- 어두운 부분의 질감과 가는 선이 읽히는가?

## 4. 링크 미리보기 연결

작품의 `index.html`에 정적 메타 태그를 넣는다. 클라이언트 JavaScript 실행 뒤에만 추가되는 태그로 구현하지 않는다.

- `canonical`, `og:url`: 확인된 공개 배포 호스트와 작품 경로
- `og:type`: `website`
- `og:title`, `og:description`: 작품 제목과 짧은 설명
- `og:image`: `https://<public-host>/pages/<artwork>/assets/og-image.png` 형태의 절대 URL
- `og:image:type`: `image/png`
- `og:image:width`, `og:image:height`: `1200`, `630`
- `og:image:alt`: 실제 캡처 장면을 설명하는 대체 텍스트
- `twitter:card`: `summary_large_image`
- `twitter:title`, `twitter:description`, `twitter:image`, `twitter:image:alt`: Open Graph의 해당 값과 일치

공개 호스트와 배포 경로는 기존 프로젝트 설정에서 확인한다. 로컬 개발 주소나 Tailnet 내부 주소를 공개 카드의 이미지 주소로 쓰지 않는다. 기존 이미지의 확장자를 바꾸면 메타 태그·테스트도 함께 수정하고, 더 이상 참조하지 않는 이전 파일은 정리한다.

## 5. 빌드·배포 검증과 마무리

1. `pnpm test pages/<artwork>`와 `pnpm typecheck`를 실행한다. 테스트는 Vitest의 `test`·`expect`로 작성한다.
2. `pnpm build` 후 `dist/pages/<artwork>/assets/og-image.png`가 원본과 같은 파일인지 확인한다. 이 저장소는 작품별 `assets/`를 정적 복사하므로, 해당 경로에서 누락되거나 중복 폴더가 생기지 않아야 한다.
3. 개발 서버에서 이미지 요청이 HTTP 200과 `Content-Type: image/png`로 응답하는지 확인한다. 원본 HTML에 공유 태그가 있는지도 검사한다.
4. 배포한 경우에만 공개 HTML과 이미지 URL도 확인한다. 공개 주소가 404이거나 아직 배포하지 않았다면 “파일·메타데이터 준비 완료, 공개 미리보기는 미검증”으로 구분한다. 이를 해결하려고 승인 없이 머지하거나 배포하지 않는다.
5. 공개 주소가 정상이어도 기존 공유 미리보기가 즉시 갱신된다고 보장하지 않는다. 해당 서비스의 재조회 절차가 필요한지 확인한다.
6. 작업용 캡처·측정 파일은 정리하고 최종 PNG와 제품 코드·테스트·공통 가이드만 커밋한다. 관련 없는 게시물 캡션은 로컬에 추가하지 않는다.
7. 커밋·푸시 후 기존 Draft PR을 갱신한다. 결과를 전달할 때는 최종 이미지와 이 가이드의 경로를 함께 안내한다.
