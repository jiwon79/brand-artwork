# Graphics Explanation Writing Guide

이 문서는 Brand Artwork의 그래픽스·수학·렌더링 구현을 설명할 때 따라야 하는 작성 기준이다. 특정 작품에 종속된 설명이 아니라, 앞으로 추가되는 모든 artwork와 concept 문서에 공통으로 적용한다.

목표는 전문용어를 줄이는 것만이 아니다. **직관, 공간 관계, 수식, 실제 코드 사이의 연결이 한 단계도 끊기지 않게 설명하는 것**이다.

## 1. 독자에 대한 기본 가정

다음 수준의 독자를 기준으로 작성한다.

- TypeScript, GLSL, 함수 호출과 데이터 흐름은 읽을 수 있다.
- 벡터, normal, tangent, SDF, reflection 같은 용어를 본 적이 있다.
- 그래픽스 수학을 실제 작품 코드와 연결하며 체계화하는 중이다.
- 공식을 계산하는 것보다 그 공식이 왜 필요한지 먼저 알고 싶어 한다.
- 추상적인 정의보다 위치, 방향, 전후 변화가 보이는 그림으로 더 잘 이해한다.
- 구현이 동작한다는 사실뿐 아니라 일반적인 방법인지, 근사인지, 한계는 무엇인지 확인하고 싶어 한다.

따라서 설명을 지나치게 초보적으로 단순화하거나, 반대로 전문용어만으로 압축하지 않는다. **고등학생도 따라갈 수 있는 직관에서 출발하되 실제 수식과 코드까지 도달해야 한다.**

## 2. 설명의 기본 연결 구조

하나의 개념은 가능하면 다음 순서로 설명한다.

```text
해결하려는 문제
  -> 공간에서 무엇이 어디에 있는가
  -> 어떤 값을 입력으로 받는가
  -> 중간값은 무엇을 측정하는가
  -> 값이 커지거나 작아지면 무엇이 바뀌는가
  -> 실제 수식
  -> 왜 그 수식이어야 하는가
  -> 코드에서 어떻게 구현하는가
  -> 결과가 다음 단계에서 어떻게 사용되는가
  -> 일반적인 이름, 한계, 대안
```

중간 단계를 생략한 채 `부드럽게 보간한다`, `미분으로 변화량을 구한다`처럼 결론만 쓰지 않는다.

## 3. 항상 문제부터 설명한다

함수 이름이나 공식을 먼저 제시하지 않는다. 그 계산이 없으면 어떤 문제가 생기는지 먼저 설명한다.

좋지 않은 설명:

> `inverseBoundarySpecWarp()`는 mean-value coordinates를 계산한다.

좋은 설명:

> 늘어난 외곽선과 원의 경계 기둥은 서로 대응하지만, 내부 픽셀 `P`의 원래 위치는 아직 모른다. `inverseBoundarySpecWarp()`는 이 내부 위치를 복원하기 위해 각 기둥의 weights를 계산한다.

독자가 `왜 이 계산을 하는가?`에 답할 수 있어야 다음 수식으로 넘어간다.

## 4. 정밀 도형은 SVG로 만들고 draw.io에서 설명을 조립한다

다음과 같은 내용은 텍스트 그림이나 ASCII 도식에 의존하지 않는다.

- 점, 선, 면의 위치 관계
- normal, tangent, ray 같은 방향 벡터
- 회전 전후의 대응
- cage 기둥과 index 대응
- 외곽선 추출 과정
- 거리나 각도에 따른 weight 변화
- 여러 좌표 공간 사이의 변환

이 경우 `docs/assets/`에 결정적인 SVG를 만들고 문서의 수식보다 먼저 배치한다.

그림 전체를 한 도구에서 억지로 완성하지 않는다. 역할을 다음처럼 나눈다.

| 구성 요소 | 제작 도구 | 이유 |
| --- | --- | --- |
| 곡선, blur, gradient, 정밀한 외곽선, 픽셀 형태 | SVG | 형태와 효과를 정확하게 제어할 수 있다. |
| 제목, 본문 라벨, 번호, 화살표, 패널 배치, 설명선 | draw.io | 문장과 흐름을 쉽게 정렬하고 수정할 수 있다. |
| 문서에 삽입하는 완성 그림 | draw.io에서 export한 SVG | 정밀 도형과 설명을 하나의 이미지로 전달할 수 있다. |

기본 제작 흐름은 다음과 같다.

1. 설명의 핵심이 되는 정밀 도형을 투명 배경 SVG로 만든다.
2. SVG에는 설명 문장이나 화살표를 넣지 않고, 도형과 효과만 남긴다. 접근성을 위한 `<title>`과 `<desc>`는 유지한다.
3. draw.io에 이 SVG를 이미지 객체로 삽입한다.
4. draw.io에서 제목, 라벨, 화살표, 비교 패널과 읽는 순서를 구성한다.
5. draw.io 편집 정보가 포함된 최종 SVG로 export하고 Markdown에는 이 최종 SVG를 삽입한다.

파일은 다음 세 층으로 보관한다.

```text
docs/assets/<name>-geometry.svg  정밀 도형 원본
docs/assets/<name>.drawio       설명과 배치 편집 원본
docs/assets/<name>.svg          문서에 삽입하는 최종 결과
```

- draw.io 기본 도형으로 곡선, blur, gradient나 렌더링 결과를 비슷하게 다시 그리지 않는다.
- 삽입한 SVG는 draw.io 안에서 하나의 이미지 객체로 취급한다. 내부 형태를 수정할 때는 `-geometry.svg`를 고친 뒤 draw.io에 다시 반영한다.
- 저장 위치에 의존하는 로컬 파일 링크 대신 SVG 데이터를 draw.io 파일 안에 포함해 다른 환경에서도 깨지지 않게 한다.
- 최종 SVG를 export할 때는 draw.io 편집 정보를 함께 포함해 결과 파일도 다시 열어 수정할 수 있게 한다.
- 단순한 직사각형 구조도처럼 정밀 도형이 전혀 필요 없는 경우에는 `-geometry.svg` 없이 draw.io만 사용해도 된다.

### 정밀 SVG 작성 규칙

- 한 그림은 가능하면 2~3개 패널로 제한한다.
- 패널은 왼쪽에서 오른쪽으로 실제 계산 순서를 따른다.
- 같은 대상은 모든 패널에서 같은 색과 형태를 사용한다.
- 변수 이름, index, 방향 화살표처럼 읽기 위한 표시는 최종 draw.io 조립 단계에서 추가한다.
- 정밀 도형 안에 반드시 붙어 있어야 하는 기호만 SVG에 남기고, 설명용 텍스트는 중복해서 넣지 않는다.
- 색상만으로 의미를 구분하지 않고 라벨과 선 모양을 함께 사용한다.
- 설명용 축소 개수와 실제 코드 개수가 다르면 둘을 명시한다.
- SVG에 `<title>`, `<desc>`, `role="img"`를 넣는다.
- 작은 본문 크기로 보아도 라벨이 겹치거나 잘리지 않아야 한다.
- 완성 후 기존 Chrome 창에서 실제 렌더링을 확인한다.

### draw.io 조립 규칙

- 패널은 왼쪽에서 오른쪽 또는 위에서 아래로 실제 계산 순서를 따른다.
- 화살표가 다른 화살표나 패널을 가로지르지 않도록 행과 열을 먼저 정한 뒤 연결한다.
- 같은 종류의 라벨은 글꼴, 크기, 정렬과 여백을 통일한다.
- SVG 위에 라벨을 겹칠 때 핵심 곡선이나 blur 경계를 가리지 않는다.
- 최종 export 후 글자 잘림, 화살표 교차, SVG 비율 왜곡과 흐릿한 확대가 없는지 확인한다.

텍스트는 그림에서 이미 보이는 내용을 장황하게 반복하지 않고, 그림을 읽는 순서와 핵심 관계만 설명한다.

## 5. 비유는 실제 구현과 바로 연결한다

고무판, 울타리, 모눈종이 같은 비유는 출발점으로 유용하다. 하지만 비유만 남기지 않고 실제 데이터에 대응시킨다.

```text
울타리 기둥
  -> boundary cage vertex D_i

모눈종이 교차점의 숫자
  -> SDF sample

늘이기 전 고무판
  -> canonical coordinate
```

비유가 설명하지 못하는 한계도 적는다. 예를 들어 cage 번호가 같은 물질점을 완벽하게 추적하지 않는다면 울타리 비유 뒤에 그 사실을 명시한다.

## 6. 변수는 등장하는 즉시 정의한다

수식 전에 기호 표를 제공한다. 하나의 대상에 여러 이름을 섞어 쓰지 않는다.

| 구분 | 작성 기준 |
| --- | --- |
| 위치 | `point`, `P`, `specPoint`처럼 좌표임을 밝힌다. |
| 방향 | `normal`, `ray`, `reflection`처럼 위치가 아닌 벡터임을 밝힌다. |
| 거리 | 단위와 부호의 의미를 밝힌다. |
| 각도 | degree인지 radian인지 밝힌다. |
| weight | 고정값인지 픽셀마다 계산하는 값인지 밝힌다. |
| index | 어떤 시작점과 진행 방향을 기준으로 붙는지 밝힌다. |

설명 중 변수 이름을 바꿔야 한다면 두 이름의 대응을 먼저 선언한다.

```text
설명에서 P = shader의 point
설명에서 C_i = cage texture의 zw 좌표
```

## 7. 수식은 네 단계로 설명한다

수식을 제시할 때는 반드시 다음 네 단계를 포함한다.

### 7.1 각 항이 무엇을 측정하는가

```text
r_i     P와 기둥 사이의 거리
alpha_i P에서 본 이웃 edge의 각도
t_i     edge의 각도 영향
q_i     정규화 전 weight
w_i     합이 1인 최종 weight
```

### 7.2 값이 변하면 결과가 어떻게 변하는가

```text
r_i 감소
  -> 기둥이 가까움
  -> 해당 기둥의 weight 증가

alpha_i 증가
  -> P에서 edge가 더 넓게 보임
  -> angle weight 증가
```

가능하면 `0`, 중간값, 극한값을 비교한다.

### 7.3 실제 수식은 그다음에 제시한다

```text
t_i = tan(alpha_i / 2)
q_i = (t_(i - 1) + t_i) / r_i
w_i = q_i / sum(q)
```

### 7.4 왜 그 형태인지 설명한다

`공식이라서`, `일반적으로 사용해서`로 끝내지 않는다. 가능한 범위에서 기하학적 이유나 항등식을 보여준다.

```text
두 unit vector의 합 길이  = 2 * cos(alpha / 2)
두 unit vector의 차 길이  = 2 * sin(alpha / 2)

합을 차와 같은 길이로 바꾸는 비율
  = sin(alpha / 2) / cos(alpha / 2)
  = tan(alpha / 2)
```

완전한 증명이 문서 흐름을 방해하면 architecture에는 직관만 남기고 별도 concept 문서에서 유도한다.

## 8. 좌표 공간과 단위를 빠뜨리지 않는다

그래픽스 설명에서 같은 `x`, `y`처럼 보여도 서로 다른 공간일 수 있다. 다음 항목을 명시한다.

- CSS pixel인지 device pixel인지
- 정규화된 `[-1, 1]` 좌표인지 texture `[0, 1]` UV인지
- 화면 위치인지 3D 방향인지
- 변형된 현재 좌표인지 canonical 좌표인지
- 길이 1로 normalize된 벡터인지

특히 `direction`, `position`, `sample coordinate`를 혼동하지 않게 한다.

```text
canonicalPoint : 기준 형태 안의 2D 위치
surfaceNormal  : 표면의 3D normal 방향
sampleDirection: texture나 환경을 조회하는 3D 방향
```

## 9. 계산 빈도와 저장 위치를 설명한다

값이 언제 계산되는지 알아야 비용과 역할을 이해할 수 있다.

다음 중 어디에 해당하는지 명시한다.

- 초기화할 때 한 번
- 입력이나 외곽선이 바뀔 때 CPU에서 다시 계산
- 매 frame 계산
- 매 vertex 계산
- 매 fragment 또는 pixel 계산
- texture나 buffer에 미리 저장

예를 들어 `w_i`가 cage에 저장된 고정값인지, 각 픽셀 `P`마다 GPU가 새로 계산하는 값인지 반드시 구분한다.

## 10. 수식과 계산 흐름을 연결한다

함수 이름만 나열하지 않고 입력, 중간값, 출력, 다음 소비자를 연결한다.

```text
입력
  deformed point P
  deformed cage D_i
  canonical cage C_i

중간 계산
  r_i -> t_i -> q_i -> w_i

출력
  canonicalPoint

다음 단계
  원본 속성 또는 texture 조회
```

Concept 문서에서는 특정 작품의 파일명이나 함수명을 사용하지 않고, 수식을 이해하는 데 필요한 일반 pseudocode만 제시한다. 실제 파일과 함수 링크, CPU와 GPU 구현의 역할 차이는 `artworks/<name>/` 문서에서 설명한다.

코드가 수학 공식을 최적화해 다른 모양으로 작성되어 있다면 동치 관계도 보여준다.

```text
수학 설명
  q_i = (t_(i-1) + t_i) / r_i

shader 구현
  edge i를 순회하며 t_i / r_i를 양 끝 기둥에 누적
```

## 11. 일반 원리와 작품 전용 응용을 문서 경계로 분리한다

다음 세 층을 한 Concept 본문에 섞지 않는다.

1. 그래픽스에서 공통적으로 쓰이는 개념
2. 여러 선택지 중 이 작품이 선택한 방법
3. 작품의 미감을 위해 추가한 경험적 근사

예:

```text
공통 개념
  generalized barycentric coordinates

선택한 방법
  mean-value coordinates

특정 작품 전용 응용
  artworks/<name>/architecture.md에서 설명
```

Concept에는 1번과 일반적으로 재사용 가능한 2번까지만 둔다. 작품의 미감을 위한 값, pass 순서, 함수명, `heuristic`은 artwork 문서로 옮긴다. Concept에서 실제 사례가 필요하면 문서 끝의 `구현 참고`에 artwork 문서 링크만 둔다.

## 12. 한계와 대안을 숨기지 않는다

설명 마지막에는 현재 방식이 보장하지 않는 것을 적는다.

- 큰 변형에서도 안정적인가?
- 오목한 모양이나 topology 변화에서 어떻게 되는가?
- 정확한 물질점을 추적하는가, 둘레 비율을 대응시키는가?
- 비용은 픽셀 수나 기둥 수에 어떻게 비례하는가?
- 어떤 상황에서는 다른 방법이 더 적합한가?

한계를 먼저 나열해 핵심 흐름을 방해하지 말고, 기본 원리를 설명한 뒤 별도 절로 둔다.

## 13. 피해야 하는 표현

다음 표현은 계산 과정을 생략하므로 단독으로 사용하지 않는다.

| 피할 표현 | 대신 설명할 내용 |
| --- | --- |
| `부드럽게 보간한다` | 어떤 값으로 weight를 만들고 왜 연속적인지 |
| `자연스럽게 바뀐다` | 입력이 조금 변할 때 어떤 중간값이 조금 변하는지 |
| `미분으로 변화량을 구한다` | 무엇을 어느 방향으로 얼마나 움직였을 때의 변화인지 |
| `일반적인 공식이다` | 기법의 이름, 사용 분야, 이 구현이 선택한 이유 |
| `기둥의 영향을 섞는다` | 거리·각도·정규화로 weight를 만드는 과정 |
| `이름보다 역할이 중요하다` | 이름과 역할을 모두 설명하고 수식·코드에 연결 |

전문용어를 없애는 대신 처음 등장할 때 한국어 역할을 함께 쓴다.

```text
seam: 닫힌 외곽선에서 0번 index가 시작되는 기준점
canonical: 변형 전의 기준 좌표
inverse warp: 현재 출력 위치에서 원래 위치를 역으로 찾는 변환
```

## 14. Architecture와 Concepts 문서의 역할을 나눈다

### `docs/artworks/<name>/architecture.md`

- 현재 작품의 실제 실행 순서
- 주요 모듈과 데이터 흐름
- 각 단계가 필요한 이유
- 현재 코드의 파라미터와 구현 선택
- 자세한 공통 원리를 설명하는 concept 링크

Architecture에서 긴 수학 유도를 반복하지 않는다.

### `docs/concepts/<concept>.md`

- 다른 작품에도 재사용할 수 있는 원리
- SVG를 이용한 공간 관계
- 변수 정의와 수식 유도
- 일반적인 사용 분야
- 구현상의 특수 상황과 대안
- 특정 작품명·함수명·기본값·pass 구성이 없는 일반 pseudocode
- 문서 끝에서 artwork 문서로 연결하는 짧은 `구현 참고`

하나의 architecture 절이 지나치게 길어지면 작품 전용 흐름만 남기고 공통 수학을 concepts로 분리한다.

## 15. 권장 Concept 문서 템플릿

```markdown
# [Concept Name]

한 문장 정의와 이 개념이 해결하는 문제.

## 1. 그림으로 먼저 보기

![입력에서 결과까지 설명하는 SVG](../assets/example.svg)

## 2. 해결하려는 문제

이 계산이 없을 때 생기는 문제.

## 3. 입력과 출력

변수 표와 좌표 공간.

## 4. 직관적인 계산 과정

값의 증가·감소와 결과 변화.

## 5. 실제 수식

각 항의 의미와 계산 순서.

## 6. 왜 이 수식인가

기하학적 이유 또는 유도.

## 7. 일반 pseudocode

수학식과 계산 순서의 대응. 특정 작품 함수명은 사용하지 않는다.

## 8. 일반적인 사용

재사용 가능한 적용 분야.

## 9. 특수 상황과 한계

근사, 비용, 실패 가능성, 대안.

## 10. 구현 참고

이 원리를 사용하는 artwork 문서 링크만 간단히 제공.

## 11. 핵심 요약

입력 -> 중간값 -> 출력 한 줄 흐름.
```

## 16. 작성 전후 체크리스트

### 작성 전

- [ ] 실제 코드를 읽었다면 공통 원리와 작품 전용 구현을 먼저 분리했다.
- [ ] 이 내용이 artwork 구조인지 재사용 가능한 concept인지 구분했다.
- [ ] 독자가 가장 먼저 물을 `왜 필요한가?`를 정했다.
- [ ] 위치·방향 관계에 SVG가 필요한지 판단했다.

### 작성 후

- [ ] 입력, 출력, 다음 소비자가 연결되어 있다.
- [ ] 모든 변수는 등장할 때 정의되어 있다.
- [ ] 좌표 공간과 단위가 명시되어 있다.
- [ ] 값이 커지거나 작아질 때의 결과가 설명되어 있다.
- [ ] 수식의 각 항뿐 아니라 수식 형태의 이유도 설명되어 있다.
- [ ] Concept의 변수 이름이 수식 및 SVG와 일치한다.
- [ ] Concept 본문에 작품명, 작품 함수명, 현재 기본값, pass 구성이 없다.
- [ ] 작품 적용 사례는 마지막 `구현 참고`의 artwork 문서 링크로만 연결했다.
- [ ] 한계와 대안을 기본 흐름 뒤에 적었다.
- [ ] 핵심 공간 관계를 ASCII 그림에 의존하지 않았다.
- [ ] SVG의 라벨 겹침과 문서 링크를 실제로 검증했다.

## 17. 최종 원칙

좋은 설명은 쉬운 단어만 사용하는 설명이 아니다.

> 독자가 `무엇을 하는가`에서 멈추지 않고 `왜 필요한가`, `왜 이 수식인가`, `어디까지 정확한가`까지 한 흐름으로 따라갈 수 있어야 한다. 실제 코드 위치는 artwork 문서에서 이어진다.
