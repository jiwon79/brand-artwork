# Instagram assistant

Local Instagram record viewer and Codex-operated reply service for a Business or Creator account. It uses Meta's **Instagram API with Instagram Login** (`graph.instagram.com`) to read media, comments and supported DM conversations, and to send approved replies. It never uses Instagram's private/mobile endpoints or asks for an Instagram password. The browser UI can manually sync and view records; it does not classify, draft, send replies, react, or change Instagram settings.

Instagram DM 답변을 준비하거나 보내기 전에는 Notion `Project → Vibe → 내부 운영`의 [Instagram DM 답변 규칙](https://app.notion.com/p/3e7a89f7e31a815b8b60c3ead057bf0a)을 읽는다. 문구, 분기, 메시지 분할과 대화별 승인 기준은 그 문서에서 관리한다. 자동 분류와 자동 발송은 사용하지 않는다.

## Meta setup

1. Create a Meta app with **Instagram API with Instagram Login** and enable Business Login for Instagram. Add the Instagram professional account to the app (or obtain the necessary access level for other accounts).
2. Grant `instagram_business_basic`, `instagram_business_manage_comments`, and `instagram_business_manage_messages`.
3. Register a redirect URI that reaches this app's `/api/auth/callback` endpoint. Meta must be able to redirect the browser to it. If Meta rejects a local HTTP URI, use an HTTPS tunnel or deployment that forwards to this local app.
4. Copy `.env.example` to `.env.local` and enter separate `META_DEV_*` and `META_PROD_*` app credentials and **exact** registered redirect URIs. Select one app with `INSTAGRAM_ENV=development` or `production`. The two app IDs must differ. `.env.local` is gitignored; keep it private (`chmod 600 .env.local`). Do not put credentials in chat, Git, or Notion.
5. Start `./start.command`. Codex can request a protected OAuth URL with `POST /api/auth/url`; sign in and grant access on Instagram's own authorization page. The app stores the resulting long-lived Graph token in `~/Library/Application Support/InstagramAssistant/graph-token.json` with mode `0600`; it refreshes near expiry. Old private API login files are not used.

Meta's Instagram Login setup says an app must be published to access live data. Direct developers using only their own Instagram business can skip App Review, but publishing still requires a public privacy-policy URL. The site's policy source is `public/instagram-assistant-privacy.html`; use its deployed URL only after confirming the public page loads. An unpublished app can report a nonzero `comments_count` while returning an empty `/{media_id}/comments` list; the assistant treats that mismatch as an error instead of an empty inbox.

The app binds to `127.0.0.1:4318`. `INSTAGRAM_ASSISTANT_DATA` overrides the shared data directory. Run only one assistant process against it at a time. `INSTAGRAM_GRAPH_VERSION` can select the Meta API version after checking its current documentation. The legacy `INSTAGRAM_APP_*` environment names only work when `INSTAGRAM_ENV` is unset, for the existing loopback installation during migration.

## Turso and administrator login

Set distinct `TURSO_DEV_DATABASE_URL`/`TURSO_DEV_AUTH_TOKEN` and `TURSO_PROD_DATABASE_URL`/`TURSO_PROD_AUTH_TOKEN` values. The Vercel Marketplace connection with prefixes `TURSO_DEV_` and `TURSO_PROD_` instead creates `TURSO_DEV_TURSO_DATABASE_URL`/`TURSO_DEV_TURSO_AUTH_TOKEN` and their production equivalents; these are also accepted. `INSTAGRAM_ENV` selects the matching database. The same URL for both environments is rejected. `TURSO_DRIVER=libsql` uses the libSQL Turso service; set `TURSO_DRIVER=turso` for the newer Turso Database engine. An unset URL keeps local SQLite for development. The remote driver uses direct network queries, so no writable local SQLite file is needed in a hosted process.

To preserve the current records, configure the destination Turso environment, then run `uv run --env-file .env.local python -m app.migrate_to_turso`. Migration takes a consistent SQLite snapshot, accepts an otherwise empty database with automatically initialized settings and artworks, copies the record tables, and checks row counts. If the local viewer or webhook kept writing during the snapshot, stop those writers at cutover and call `app.migrate_to_turso.reconcile_recent(source_path, snapshot_start_iso)` before changing Meta's callback URL. Delta reconciliation copies records while preserving the hosted full-sync cursor, settings, and encrypted Meta token. Keep the source SQLite file as a rollback copy until the hosted records have been inspected. Copy an existing local Meta token into Turso with `app.token_store.save_token` using the same `INSTAGRAM_TOKEN_ENCRYPTION_KEY` configured on the hosted project, or reconnect through OAuth. `uv run python -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'` generates a new private key. The Meta access token is encrypted in Turso, while OAuth state is stored there until callback completion.

Set `ADMIN_PASSWORD_HASH` and `ADMIN_SESSION_SECRET` before exposing the viewer. Generate a password hash locally with `uv run python -m app.admin_auth` (it prompts without echoing the password), and generate a random session secret with a password manager. In `.env.local`, wrap the hash in single quotes so dotenv does not expand its `$` separators: `ADMIN_PASSWORD_HASH='pbkdf2_sha256$...'`. The browser receives a 12-hour HttpOnly session cookie after login; API records and actions require that session, and mutations require a same-origin request. An external host without these settings returns 503. Loopback keeps the existing local-token workflow until admin login is configured. Deploy development and production as separate services with different Meta apps and Turso databases.

Vercel variables stored as sensitive are masked when pulled back to `.env.local`. Retain the administrator password, webhook verify token, and token encryption key in a secure local store for testing, migration, and future rotation; an empty value in an env pull does not show that the deployment lacks the variable.

For Vercel, set the project root directory to `instagram-assistant`; `index.py` exports the combined FastAPI app. The public `/webhook` verifies and stores signed events, then processes the affected thread after acknowledging the request through a FastAPI background task. The Vercel cron drains any queued events once daily at 02:00 KST. The GitHub Actions `Instagram assistant daily full sync` workflow scans accessible media and DMs at 03:00 KST; its 15:00 KST run resumes an unfinished pass. Configure repository secrets `INSTAGRAM_TURSO_PROD_URL`, `INSTAGRAM_TURSO_PROD_TOKEN`, and `INSTAGRAM_TOKEN_ENCRYPTION_KEY` with the production Turso connection and the same encryption key used by Vercel. The workflow uses a shared concurrency group and the database cursor to avoid overlapping or repeating a completed pass within 24 hours. Keep the development and production deployments in separate Vercel projects with distinct environment variables. The existing local `app.webhook:app` processes events as they arrive.

## Webhook and daily reconciliation

The separate `app.webhook:app` process binds to `127.0.0.1:4319`. Expose only that process at a public HTTPS `/webhook` URL. Never expose the viewer on port 4318 through the public webhook tunnel. Configure each Meta app's callback with its own URL and `META_DEV_WEBHOOK_VERIFY_TOKEN` or `META_PROD_WEBHOOK_VERIFY_TOKEN`; subscribe to `messages`, `message_reactions`, and `comments`. Activate those fields for the connected account with the administrator-protected `POST /api/webhooks/subscribe` endpoint, which reads back `/me/subscribed_apps` to confirm the result. The webhook endpoint checks Meta's SHA-256 signature against the matching app secret (or an explicit `META_*_WEBHOOK_APP_SECRET` override), stores the raw notification in the selected Turso/SQLite database, acknowledges it, then queries only the affected DM conversation or comment thread. Failed lookups are retried; the viewer does not send anything in this flow. Instagram's webhook `entry.id` can be the account's messaging ID, distinct from Graph `/me` ID; the assistant records that ID from a verified conversation participant before accepting its events.

Run `uv run --env-file .env.local python -m app.full_sync` once daily from the local scheduler only when using the local deployment. That command scans every accessible media or DM conversation with all its accessible comments, replies, or messages, saving the pagination cursor after each item. A Meta request-limit response pauses the local scan for one hour without losing that cursor. In production, GitHub Actions resumes an incomplete pass at its next scheduled run. A completed pass waits 24 hours before starting again. Meta omits request-folder conversations inactive for more than 30 days. The last successful complete pass is stored as `last_full_sync_at`; `full_sync_progress` shows the current phase. Existing `app.worker` and viewer manual sync remain partial, on-demand operations.

## Review and sending

- [`./assistant`](./assistant) is Codex's operating interface. Run `./assistant --env prod --help` in this directory for its options. `review --limit 10` returns ten active DM conversations with their full stored message context in compact JSON; `--offset` continues through the queue and `--skip-user NAME` excludes an explicit hold. The record is only as current as its last successful sync. Other reads are `conversations --status active`, `conversation 'THREAD_ID'`, and `events --kind comment --status active --limit 10`. Use `sync --scope dm --user-id 'INSTAGRAM_SCOPED_USER_ID'` for one DM conversation after a Chrome heart, or `heart-observed 'comment:COMMENT_ID' --yes` only after confirming that exact comment's heart in Chrome. A single reply uses its approved saved draft and `send 'EVENT_ID' --expect-draft '승인된 답장' --yes`.
- For approved, separately numbered DMs, put only the approved conversations and exact message splits in a local JSON file, then run `./assistant --env prod send-batch /path/to/approved-dms.json --yes`. Example: `[{"event_id":"dm:MESSAGE_ID","username":"recipient","messages":["첫 DM","둘째 DM"]}]`. Keep this temporary file out of Git and remove it after use. The CLI checks every account before the first send, then sends messages in order, stops on the first failure, and reports which earlier conversations completed. The server saves each sequence before sending and never automatically retries an uncertain item; check Instagram before another attempt. Verify the exact messages in the conversation after sending. Do not include a held conversation in the file.
- Hosted CLI calls need the administrator password through Keychain, `INSTAGRAM_ASSISTANT_ADMIN_PASSWORD`, `--password-stdin`, or an interactive prompt. Production also recognizes the existing `Instagram Assistant Admin` Keychain entry after checking `Instagram Assistant Prod Admin`. An existing Chrome login does not authenticate the CLI. Keep the password out of command arguments, chat, Git, and Notion. [Backend API reference](./API.md) is for implementation and troubleshooting; routine review and sending use the script.
- The browser UI exposes no local mutation token. Its sync button calls a same-origin, sync-only endpoint; all reply and reaction actions remain protected from the browser. For hosted operations, Codex uses `./assistant`; the local worker and backend API remain available for maintenance and diagnostics.
- New OAuth connections reset automatic sending to off. Codex prepares and sends only the individual replies approved for that batch.
- Comments are sent with `POST /{comment_id}/replies`, not `POST /{media_id}/comments`. Before sending, the assistant checks the parent's replies for an existing account reply. After sending, it looks for the returned reply ID under that parent. An uncertain result is left for manual review and is never automatically retried.
- Comment review is computed per parent thread from its stored replies. The thread stays in `확인 필요` only while its latest inbound comment or reply has no later recorded action. An account reply, observed heart, or protected ignore/review action moves it to `완료`; a newer inbound reply reopens it. Threads sort by their latest activity. The original comment's `sent` history is preserved.
- The comment list shows a short post name and separate post/original-comment links instead of the caption. Existing artwork titles appear automatically; use `별명 수정` to assign a persistent short name to other posts or override an artwork title.
- DM replies use the official Send API and require an Instagram-scoped sender ID. Meta only allows supported conversations and messages; historical request-folder messages may not all be available through the API. Accept a request in Chrome when needed, then send text through the script. Use Chrome for hearts and request acceptance, not routine text sending.
- Press both comment and DM hearts in the existing Instagram Chrome session after item-specific approval. Reload Instagram to verify the heart stayed on the exact item. For DMs, run a targeted `./assistant --env prod sync --scope dm --user-id 'INSTAGRAM_SCOPED_USER_ID'` and confirm the stored reaction on that message. The official comment API does not expose whether this account liked a comment; after verifying the heart in Chrome, run `./assistant --env prod heart-observed 'comment:COMMENT_ID' --yes` or click that comment's `Chrome에서 하트 눌렀음 · 완료로 기록` button in the hosted viewer. Confirm the thread left `확인 필요` and entered `완료`. This records an observed result for one comment; it does not press a heart. A sync alone cannot infer an account heart from `like_count`, which includes other people's likes. The browser viewer never sends reactions. The legacy Meta DM reaction endpoint remains in code but is not part of the current operating flow because its live test returned HTTP 500/code 2 without a heart.
- DM reaction webhooks record both participants' emoji and removals directly. Reactions that arrive before their messages remain pending until a later message sync. Graph message reaction snapshots reconcile both sides, and the viewer shows the other participant's reaction on sent messages. `python -m app.reaction_backfill --apply` replays previously stored signed reaction webhooks once after upgrading an existing database.
- Legacy events remain in SQLite for history, but can only be sent if their account ID matches the active official connection. Events without a verified account ID cannot be sent.
- Daily send limit defaults to 20. Meta API limit responses halt sending.

The previous assistant's full private-API DM history, private reaction state, and some shared-post details cannot be recovered by the official conversation read API. The app does not claim that an initial DM sync is a complete historical archive. Confirm the scope returned for the connected account before enabling automatic DM replies.

## Run and tests

```bash
./start.command
uv run pytest
```

For a single read-only sync: `uv run python -m app.worker`. This command never classifies or sends replies.
